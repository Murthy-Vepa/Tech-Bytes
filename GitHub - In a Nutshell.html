    What is GitHub?

    GitHub is the world's largest AI-powered developer platform — a cloud-based service built on top of Git that enables individuals and organizations to host, version-control, review, collaborate on, automate, and secure software projects at any scale. With over 100 million developers and more than 420 million repositories, GitHub is the central hub for open-source software and enterprise development worldwide.

    While Git is a distributed version control system you run locally, GitHub adds an entire ecosystem on top of it:

    • Remote repository hosting — store and sync code across teams and geographies
    • Collaboration tooling — pull requests, code reviews, issues, discussions, and projects
    • CI/CD automation — GitHub Actions pipelines to build, test, and deploy automatically
    • Security features — secret scanning, Dependabot, CodeQL code scanning, and branch protection
    • AI pair programming — GitHub Copilot embedded directly into your editor and workflow
    GitHub is not just a Git host.
    It is a complete DevSecOps platform covering the entire software development lifecycle — from idea to deployment — with AI, automation, security, and collaboration built in at every layer.

    Git: The Foundation

    Git is a free, open-source distributed version control system (DVCS) created by Linus Torvalds in 2005 for managing the Linux kernel source code. It tracks changes to files over time, allowing developers to:

    • Record a complete history of every change — who made it, when, and why
    • Work in isolation on feature branches without disturbing the main codebase
    • Merge independent lines of work together with conflict detection
    • Roll back to any prior state instantly
    • Work fully offline — every clone is a complete repository with full history
    Git is the tool. GitHub is the platform.
    Git runs on your local machine. GitHub is a cloud service that hosts Git repositories and wraps them with collaboration, automation, security, and AI tooling. You can use Git without GitHub, but GitHub always uses Git under the hood.

    Core Git Concepts — Quick Reference

    📁 Repository (repo)

    A directory tracked by Git. Contains all project files plus the hidden .git/ folder that stores the full history. Can be local or cloned from a remote like GitHub.

    🌿 Branch

    A lightweight, movable pointer to a commit. Branches let work happen in parallel without interference. main (or master) is the default integration branch.

    📝 Commit

    A snapshot of the project at a point in time. Every commit has a unique SHA-1 hash, an author, a timestamp, a message, and a pointer to its parent commit(s).

    🔀 Merge

    Integrates changes from one branch into another. Git supports fast-forward merges, three-way merges, and rebase to produce a linear history.

    🔁 Remote

    A named reference to a repository hosted elsewhere (e.g., origin pointing to GitHub). git push sends local commits to the remote; git pull fetches and merges them back.

    🏷️ Tag

    A named, immutable pointer to a specific commit — typically used to mark release versions (e.g., v1.4.0). Annotated tags include a message and are stored as full Git objects.

    A repository (repo) is the fundamental unit of storage in GitHub. It contains:

    • All project files and directories (source code, docs, config, assets)
    • The complete Git history — every commit ever made

    🌿 Branches & Tags

    What is a Branch?

    A branch is a lightweight, movable pointer to a commit. Creating a branch is instantaneous — it creates a 41-byte file in .git/refs/heads/ pointing to the current commit SHA. This is what makes Git branching so cheap and fast compared to other VCS systems.

    Branches enable parallel development: every feature, bug fix, or experiment gets its own branch, isolated from the main codebase until it is reviewed and merged.

    Branch = bookmark, not a copy.
    A branch doesn't copy files — it simply records a position in the commit graph. All branches share the same object store. Switching branches (git checkout) updates your working directory by applying the diff between the two pointers.

    Tags — Marking Milestones

    A tag is a named, permanent pointer to a specific commit. Unlike branches (which move forward with every commit), tags are immutable — they always point to the same commit. Tags are used to mark release versions.

    🏷️ Lightweight Tag

    A simple pointer to a commit — just a name. No extra metadata. Created with git tag v1.0.0. Stored as a plain ref, not a full Git object. Quick and simple.

    A full Git object with tagger name, email, date, and a message. Can be GPG-signed for verification. Created with git tag -a v1.0.0 -m "Release 1.0.0". Preferred for releases.

    Branch Protection Rules

    On GitHub, you can protect branches to enforce quality gates before code can merge into important branches like main:

    ✅ Require pull request reviews
    Set minimum number of approvals (1-6). Optionally require review from code owners. Block merging if new commits are pushed after approval.
    ✅ Require status checks
    Block merge until specified CI jobs pass. Optionally require branches to be up-to-date with the base branch before merging.
    ✅ Require signed commits
    Only allow GPG- or SSH-signed commits on the protected branch — verifies commit author identity.
    ✅ Require linear history
    Disallow merge commits — only squash or rebase merges allowed. Keeps the branch history clean and bisectable.
    ✅ Restrict who can push
    Only specific users, teams, or apps can push directly to the protected branch — everyone else must go through a PR.
    ✅ Rulesets (Enterprise)
    Next-gen branch protection with layered policies, bypass actors, enforcement modes (Active / Evaluate / Disabled), and org-level inheritance.

    What is a Commit?

    A commit is a permanent, immutable snapshot of the entire repository at a specific point in time. Each commit contains:

    • Tree object — a reference to the state of the entire file tree
    • Parent SHA(s) — pointer(s) to the preceding commit(s) (merge commits have 2)
    • Author — name, email, and timestamp of who wrote the change
    • Committer — name, email, and timestamp of who committed it (may differ in rebased history)
    • Message — subject line + optional body describing what changed and why
    • SHA-1 hash — cryptographic fingerprint of all the above; the commit's unique identifier
    Commits are immutable. Once created, a commit's SHA can never change. Operations like git rebase or git commit --amend don't modify commits — they create new commits with different SHAs. This is why force-pushing rewrites history.

    Undoing Changes

    ✅ git revert (safe)

    git revert <sha>

    PR Merge Strategies

    🔀 Merge Commit

    Creates a merge commit that preserves full branch history. Best when you want a clear record of when features were integrated. --no-ff behavior.

    Before: A→B→C (feature)
    After: A→B→C→M (merge)
    🗜️ Squash & Merge

    Combines all PR commits into a single commit on the base branch. Clean linear history — great for feature branches with many WIP commits. Feature branch is discarded.

    Before: A→B→C (feature)
    After: A→D (single squash)
    ↕️ Rebase & Merge

    Replays each PR commit on top of the base branch individually. Preserves individual commits but creates perfectly linear history without a merge commit.

    Before: A→B→C (feature)
    After: A→B'→C' (replayed)

    What is GitHub Flow?

    GitHub Flow is a lightweight, branch-based workflow designed for teams that deploy continuously. It has exactly 6 steps and only one long-lived branch (main). Everything else is a short-lived feature branch merged via pull request.

    Rule #1 of GitHub Flow: Anything in main is deployable. Never commit directly to main — all work flows through pull requests. Every PR merge is a potential deployment.

    GitHub Flow — Step by Step

    1. Create a Branch

    Branch off main with a descriptive name: feature/add-oauth-login. This isolates your work completely. Branch is cheap and fast — create one for every task, no matter how small.

    git switch -c feature/add-oauth-login
    2. Add Commits

    Make small, focused commits with clear messages. Each commit should represent one logical change. Push to the remote branch early — others can follow your progress and GitHub Actions starts CI.

    Deploy the branch to a staging or production environment before merging. GitHub Actions can auto-deploy on PR open or on manual trigger. If something breaks, revert by redeploying main.

    6. Merge

    Once approved and CI passes, merge via squash (clean history) or merge commit (full context). Enable auto-delete head branches so main stays uncluttered. The deployment is now permanent.

    🌊 GitFlow Strategy

    gitflowreleasehotfixdevelop

    What is GitFlow?

    GitFlow is a structured branching model published by Vincent Driessen in 2010. It defines strict roles for different branches and a formal process for managing features, releases, and hotfixes. GitFlow is ideal for software with planned, versioned releases — libraries, SDKs, desktop applications, and mobile apps.

    GitFlow vs GitHub Flow: GitFlow has more branches and more ceremony. Use GitFlow when you need to support multiple released versions simultaneously or when your release process involves a stabilization period. For web apps that deploy continuously, GitHub Flow is simpler and faster.

    GitFlow Branch Types

    🌿 main

    Long-lived. Contains only production-ready, tagged release commits. Never commit directly to main. Every commit on main corresponds to a release version tag (e.g., v2.4.0).

    🔵 develop

    Long-lived. Integration branch where all completed features accumulate. Reflects the next release in progress. CI runs here continuously. Feature branches branch off and merge back here.

    ✨ feature/*

    Short-lived. Branch off develop, one branch per feature. Merge back into develop via PR when done. Never merge directly to main.

    🏷️ release/*

    Short-lived. Branch off develop when enough features are ready. Only bug fixes, documentation, and release prep commits allowed. Merged into both main (tagged) and develop.

    🚨 hotfix/*

    Short-lived. Branch off main to fix a critical production bug immediately. Merged into both main (tagged with a patch version) and develop to keep the fix in future releases.

    🛠️ support/*

    Long-lived (optional). Maintain legacy major versions (v1.x while v2 is in development). Branch off an old release tag on main. Rarely used except for enterprise LTS support.

    Core Concepts

    Understanding GitHub Actions requires learning five nested concepts that build on each other:

    📄 Workflow

    An automated process defined in a YAML file in .github/workflows/. A repo can have multiple workflow files. Each workflow is triggered by one or more events and contains one or more jobs.

    🎯 Event

    The trigger that starts a workflow run. Events include Git activity (push, pull_request), GitHub activity (issues, release), schedules (schedule), and manual triggers (workflow_dispatch).

    ⚙️ Job

    A set of steps that run on the same runner. Jobs run in parallel by default. Use needs: to create dependencies between jobs for sequential execution. Each job gets a fresh runner environment.

    📝 Step

    An individual task within a job — either a shell command (run:) or an Action (uses:). Steps run sequentially on the same runner and share the filesystem. A failed step fails the whole job by default.

    🔌 Action

    A reusable, standalone unit of automation — referenced with uses:. Actions come from the GitHub Marketplace (actions/checkout@v4), your org (./local-action), or any public repo. They encapsulate complex logic behind a simple interface.

    🖥️ Runner

    The server that executes the job. GitHub provides hosted runners (Ubuntu, Windows, macOS) that are provisioned fresh for every job and deleted after. You can also register self-hosted runners on your own infrastructure.

    Dependency Caching — Speed Up CI

    Caching restores previously downloaded packages from a key-based store. The cache key must be unique per dependency state (typically hashed from a lock file) so stale caches are never used:

    # npm / Node.js - uses: actions/cache@v4 with: path: ~/.npm key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }} restore-keys: | ${{ runner.os }}-node-
    # Maven / Java (or use setup-java cache built-in) - uses: actions/cache@v4 with: path: ~/.m2/repository key: ${{ runner.os }}-maven-${{ hashFiles('**/pom.xml') }}
    # NuGet / .NET - uses: actions/cache@v4 with: path: ~/.nuget/packages key: ${{ runner.os }}-nuget-${{ hashFiles('**/*.csproj') }}

    Built-in Caching via Setup Actions

    Many setup-* actions include built-in caching — the simplest approach:

    ActionCache InputWhat Gets Cached
    actions/setup-node@v4cache: 'npm' or 'yarn'~/.npm or ~/.yarn/cache
    actions/setup-python@v5cache: 'pip'~/.cache/pip
    actions/setup-java@v4cache: 'maven' or 'gradle'~/.m2 or ~/.gradle
    actions/setup-dotnet@v4(no built-in — use actions/cache)~/.nuget/packages

    Cache Key Strategy

    ✅ Exact key
    ${{ runner.os }}-npm-${{ hashFiles('package-lock.json') }}
    Cache hit only when lock file hasn't changed. Best for correctness.
    ↩️ Restore keys (fallback)
    restore-keys: ${{ runner.os }}-npm-
    Prefix match — restores closest prior cache when exact key misses. Faster than cold start even if slightly stale.
    🚨 Avoid mutable keys
    Never use ${{ github.sha }} alone as a cache key — it changes every run, guaranteeing a cache miss every time.

    What is a GitHub Release?

    A GitHub Release is a deployable software iteration built on top of a Git tag. It provides a human-readable release page with a changelog, attached binary assets, and a stable API endpoint — making it the official, versioned artifact that users and downstream systems consume.

    Tag ≠ Release. A Git tag is just a pointer to a commit. A GitHub Release wraps that tag with a title, description, attached assets (compiled binaries, checksums, SBOMs), and a published/draft/pre-release state — all discoverable via the GitHub Releases page and API.

    What is Branch Protection?

    Branch Protection Rules (and the newer Rulesets) prevent direct pushes to critical branches and enforce quality gates — required reviews, passing CI, signed commits — before any code can merge. They are the primary enforcement mechanism for compliance and code quality in GitHub.

    Branch Protection vs Rulesets: The original Branch Protection Rules apply to a single branch pattern. Rulesets (introduced 2023) are more powerful — they can apply to multiple branch patterns, can be applied at the organization level (not just repo), support bypass lists, and have an "evaluate" mode for testing before enforcement. Prefer Rulesets for new configurations.

    🔍 Secret Scanning

    secret scanningleaked secretspush protection

    What is Secret Scanning?

    Secret Scanning automatically scans your repository for known secret patterns — API keys, tokens, passwords, and certificates — and alerts you or blocks the push before secrets can be exposed. GitHub partners with 200+ service providers (AWS, Azure, Google, Stripe, Twilio, and more) to recognize their token formats.

    Two Modes: Detection vs Prevention

    🔍 Secret Scanning Alerts (Detection)

    Scans commit history — past and present — for secrets. Fires an alert when found. Partners are notified automatically (e.g., GitHub notifies AWS when an AWS key is detected so they can revoke it). Available free on all public repos.

    🛑 Push Protection (Prevention)

    Blocks the git push before it reaches GitHub if a secret pattern is detected in the incoming commits. The developer must remove the secret and force-push, or provide a bypass reason (logged in audit). Available free on public repos; GHAS for private.

    Supply Chain Security Overview

    Modern applications are largely composed of open-source dependencies — a vulnerability in any one of them can compromise your application. GitHub's supply chain security tools automatically track, alert on, and fix vulnerable dependencies:

    Dependabot — Three Capabilities

    🚨 Dependabot Alerts

    Scans your dependency manifests (package.json, pom.xml, *.csproj, etc.) against the GitHub Advisory Database. Fires an alert when a CVE is found in a dependency you use. Free for all repos.

    🔧 Dependabot Security Updates

    Automatically opens a PR to update a vulnerable dependency to the minimum safe version. Includes the CVE description and CVSS score in the PR body. Free for all repos.

    ⬆️ Dependabot Version Updates

    Proactively opens PRs to keep dependencies up to date — regardless of vulnerabilities. Configured via .github/dependabot.yml. Supports npm, Maven, NuGet, Docker, GitHub Actions, pip, and more.

    # Update Docker base images weekly - package-ecosystem: docker directory: / schedule: interval: weekly

    CodeQL — Semantic Code Scanning

    CodeQL is GitHub's static analysis engine that treats code as data — it builds a queryable database of your codebase and runs security queries against it to find vulnerabilities that pattern-matching tools miss (SQL injection via indirect data flows, XSS through multi-hop taint analysis, etc.).

    Enterprise ≠ just bigger GitHub. Enterprise adds an Enterprise Account layer above Organizations — centralizing billing, policy enforcement, SSO, audit logging, and compliance reporting across dozens or hundreds of organizations and repositories from a single admin console.

    Organizations

    A GitHub Organization is a shared account for multiple collaborators to work across many repositories. It's the primary unit of collaboration above the individual user — with member management, team hierarchies, and repository access control:

    Org RoleWhat They Can Do
    OwnerFull admin — add/remove members, manage teams, configure security settings, billing, OAuth app restrictions, delete org
    MemberCan see the org, create repos (if allowed), and join teams. Default for all org members.
    Billing ManagerManage billing and payment only — no code access
    Security ManagerManage GHAS settings, view security alerts across all repos — no code write access required
    Outside CollaboratorNon-member given access to specific repos only. Counts as a paid seat on Team/Enterprise.

    Teams

    Teams are groups within an org. Assign teams to repos with a permission level instead of adding individuals — scaling access control to hundreds of repos and developers:

    📋 Repository Permissions

    Assign a team to a repo with: Read (view/clone), Triage (manage issues/PRs), Write (push), Maintain (settings except destructive), or Admin (full repo admin).

    🌳 Nested Teams

    Teams can be nested in parent/child hierarchies. A child team inherits access from its parent. Mirror your org chart — e.g., engineering → backend → payments-api.

    💬 Team Discussions

    Teams have a built-in discussion board — separate from issues and PRs. Good for team announcements, RFCs, and decision records scoped to team members.

    🔔 @mentions

    @your-org/team-name notifies all team members in issues, PRs, and comments. Use for routing reviews to the right team without listing individuals.

    IdP-Synced Teams (Enterprise)

    On GitHub Enterprise, teams can be synchronized with your Identity Provider groups (Azure AD / Okta). When a user is added to or removed from an AD group, their GitHub team membership updates automatically — eliminating manual provisioning:

    Setup flow:
    1. Enable SAML SSO + SCIM for the org
    2. Go to Team → Settings → Team synchronization → Enable
    3. Select the IdP group to sync from (e.g., GitHub-Backend-Engineers)
    4. Members of that AD group now automatically appear as GitHub team members
    5. Remove from AD group → removed from GitHub team within minutes

    SCIM Provisioning — Automatic Member Management

    SCIM (System for Cross-domain Identity Management) extends SAML by automating user provisioning and deprovisioning. When SCIM is configured, the IdP manages org membership — no manual GitHub invites or removals:

    ➕ Provision
    User added to IdP group → automatically invited to GitHub org → team membership assigned based on group mapping.
    🔄 Update
    User's name, email, or department changes in IdP → GitHub profile updated automatically within minutes.
    ➖ Deprovision
    User removed from IdP group or disabled in IdP → automatically removed from GitHub org. No manual offboarding step needed.

    GitHub Audit Log

    The Audit Log records every significant action taken across your organization or enterprise — who did what, when, from which IP address, using which authentication method. It is immutable and retained for 180 days in the UI (streaming to external SIEM for longer retention).

    Compliance teams love the audit log. SOX auditors can verify no unauthorized merges to production branches. Security teams can investigate when a secret was accessed. HR can confirm a terminated employee's access was revoked immediately. All evidence is in one place, queryable via API or exported to your SIEM.

    What Gets Logged

    🔐 Authentication Events
    Login, logout, 2FA changes, PAT creation/revocation, SAML session, SSH key add/remove
    📁 Repository Events
    Create, delete, transfer, archive, change visibility, fork, clone (audit log only — not git operations)
    👥 Membership Events
    Add/remove org member, change role, add/remove team member, invite, accept, revoke
    ⚙️ Settings Changes
    Branch protection changes, SAML SSO enable/disable, webhook add/remove, Actions policy changes
    🤖 Actions Events
    Workflow run triggers, secret access, Actions policy changes, runner registration/removal
    🛡️ Security Events
    Code scanning alert dismissed, secret scanning alert resolved, Dependabot alert dismissed, push protection bypass

    What is GitHub Connect?

    GitHub Connect is a feature that creates a secure, one-way data connection between a GitHub Enterprise Server (GHES) instance and GitHub.com (or GHEC). It lets GHES benefit from GitHub.com's cloud capabilities while keeping code and data on-premises.

    GitHub Connect is optional and outbound-only. Enabling GitHub Connect does not push your code to GitHub.com. Only specific metadata (license seat counts, anonymous usage stats, action names, etc.) flows to GitHub.com — code stays on your GHES instance. You enable only the specific features you need.

    Enabling GitHub Connect

    Prerequisites:
    • GHES instance must be able to reach github.com over HTTPS (port 443)
    • An Enterprise account on GitHub.com that owns the GHES license
    • GHES site administrator access

    Steps:
    1. On GHES Management Console → Enterprise → GitHub Connect → Enable
    2. Authenticate with a GitHub.com account that is an enterprise owner
    3. Select the specific features to enable (each can be toggled independently)
    4. Review which data flows to GitHub.com before enabling each feature

    Why GraphQL for GitHub?

    GitHub's GraphQL API v4 at https://api.github.com/graphql lets you fetch exactly the data you need in a single request — no over-fetching, no under-fetching. It's especially powerful for GitHub Projects v2 (only accessible via GraphQL), complex dashboard queries, and scenarios requiring nested resource traversal.

    ✅ Use GraphQL when...
    • Fetching nested resources (repo → PRs → reviews → comments) in one call
    • Working with GitHub Projects v2 (required — no REST equivalent)
    • Building dashboards that need many fields across many nodes
    • Minimizing API calls to stay under rate limits
    ✅ Use REST when...
    • Simple, well-known operations (open issue, create release)
    • Testing from curl or Postman without a schema
    • Using a tool or library that only supports REST
    • Performing mutations (creating, updating, deleting resources)

    query { repository(owner: "my-org", name: "my-repo") { pullRequests(first: 20, states: OPEN) { nodes { title number author { login } reviews(first: 5) { nodes { state author { login } } } labels(first: 5) { nodes { name } } } } } }

    What are Webhooks?

    Webhooks let GitHub push event notifications to your server in real time — no polling required. When something happens on GitHub (a push, a PR opened, a workflow completed), GitHub makes an HTTP POST to your configured endpoint with a JSON payload describing the event.

    Webhooks are the foundation of GitHub integrations. CI/CD systems, Slack notifications, auto-labelers, deployment triggers, security monitors — all of these react to GitHub webhooks. You can configure webhooks at the repository, organization, or enterprise level.

    Verifying Webhook Signatures

    Always verify the X-Hub-Signature-256 header to confirm the payload came from GitHub and wasn't tampered with. Use a secret token set when creating the webhook:

    // Node.js — verify HMAC-SHA256 signature import crypto from "crypto";
    function verifyWebhook(payload, signature, secret) { const hash = "sha256=" + crypto .createHmac("sha256", secret) .update(payload) .digest("hex"); // Use timingSafeEqual to prevent timing attacks return crypto.timingSafeEqual( Buffer.from(hash), Buffer.from(signature) ); }

    Webhook Best Practices

    ⚡ Respond fast
    Return HTTP 200 within 10 seconds. Offload heavy processing to a background queue — GitHub marks the delivery failed if no response arrives in time.
    🔒 Always verify signatures
    Never process a webhook payload without verifying the HMAC-SHA256 signature. An unverified webhook endpoint is an unauthenticated trigger.
    🔁 Make handlers idempotent
    GitHub may deliver the same event multiple times (retries). Store the delivery GUID (X-GitHub-Delivery) and deduplicate before processing.
    🔍 Use the delivery log
    GitHub shows every webhook delivery attempt, payload, and response in Settings → Webhooks → Recent Deliveries. Invaluable for debugging integrations.

    Repository Health

    📄 Essential Files

    Every repo should have: README.md (what, why, how to run), CONTRIBUTING.md (how to contribute), LICENSE (usage rights), .gitignore (what not to commit), CODEOWNERS (who reviews what).

    PRs under 400 lines get reviewed faster and catch more bugs. Split large features into sequential PRs. Use draft PRs for early feedback. Link every PR to an issue for traceability.

    GitHub CLI Cheat Sheet

    The GitHub CLI (gh) brings GitHub workflows into the terminal — no browser required for most common operations:

    CommandWhat it does
    gh repo create my-app --public --cloneCreate a new repo on GitHub and clone it locally in one step
    gh pr create --fill --draftOpen a draft PR using branch name as title and commits as body
    gh pr checkout 123Check out PR #123 locally without needing the branch name
    gh pr merge --squash --delete-branchSquash-merge the current PR and delete the remote branch
    gh issue create -t "Bug: login fails" -b "Steps to reproduce..."Create an issue directly from the terminal
    gh issue list --label bug --assignee @meList all bugs assigned to you across the repo
    gh run list --workflow=ci.yml --limit 5Show the last 5 runs of a specific workflow
    gh run watchWatch a live workflow run — streams logs in the terminal
    gh run rerun --failedRe-run only the failed jobs in the last workflow run
    gh secret set MY_API_KEYSet a repo secret from stdin (prompts securely; never exposes value in shell history)
    gh release create v1.2.0 --generate-notesCreate a release with auto-generated changelog from merged PRs since last tag
    gh repo clone org/repoClone any repo you have access to (respects SSO, no PAT setup needed if authenticated)
    gh auth loginAuthenticate the CLI — supports browser, PAT, and OIDC flows
    gh api /repos/{owner}/{repo}/issues --paginateCall any REST API endpoint with automatic pagination
    gh extension install dlvhdr/gh-dashInstall a CLI extension — gh-dash gives a beautiful dashboard for PRs and issues
