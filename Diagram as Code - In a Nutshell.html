    📖 What is Diagram as Code?

    intro overview diagram-as-code

    Introduction

    Diagram as Code (DaC) is the practice of defining diagrams using plain text markup languages rather than traditional drag-and-drop graphical tools. Just like Infrastructure as Code (IaC) revolutionized infrastructure management, Diagram as Code transforms how we create and maintain technical diagrams.

    Instead of using visual editors like Visio, Lucidchart, or draw.io, you write code-like syntax that gets rendered into beautiful diagrams. This approach brings software engineering best practices—version control, code reviews, automation, and collaboration—to diagram creation.

    Core Concept

    At its essence, Diagram as Code means:

    • Text-based representation: Diagrams are defined using plain text files (Markdown, YAML, or domain-specific languages)
    • Version controlled: Store diagrams in Git alongside your code
    • Programmatically generated: Render diagrams automatically in CI/CD pipelines, documentation sites, or IDEs
    • Collaborative: Use pull requests, diffs, and code reviews for diagram changes
    • Single source of truth: Keep documentation and diagrams in sync with actual code
    💡 Key Insight: Diagram as Code treats diagrams as first-class artifacts in your codebase, making them maintainable, reviewable, and automatically up-to-date.

    Example: Simple Flowchart

    Here's how a simple flowchart looks in Mermaid (a popular DaC tool):

    B -->|Yes| C[Great!]
    B -->|No| D[Debug]

    🎯 Why Diagram as Code Matters

    benefits value purpose

    The Problem with Traditional Diagramming

    Traditional diagram tools suffer from several challenges:

    • 💰 Expensive licenses: Tools like Visio, Lucidchart require paid subscriptions
    • 📁 Binary formats: Files are opaque blobs that can't be diffed or merged
    • 🔒 Vendor lock-in: Proprietary formats trap you in specific ecosystems
    • ⏰ Maintenance burden: Diagrams quickly become outdated as code evolves
    • 👥 Collaboration friction: Difficult to review changes, resolve conflicts, or track history
    • 🚫 No automation: Can't generate diagrams from code or integrate with CI/CD

    Benefits of Diagram as Code

    1. Version Control & History

    Store diagrams as plain text in Git. See exactly what changed, who changed it, and why:

    - App --> Database
+ App --> Cache --> Database

    2. Code Reviews & Collaboration

    Review diagram changes just like code reviews. Comment on specific lines, suggest improvements, and approve changes before merging.

    3. Living Documentation

    Keep diagrams next to code. When code changes, developers update diagrams in the same pull request—no more stale docs.

    4. Automation & CI/CD Integration

    • Auto-generate diagrams from code (class diagrams from Java/C#, API docs from OpenAPI)
    • Validate diagrams in CI pipelines
    • Publish diagrams to wikis, documentation sites, or Confluence automatically
    • Generate deployment diagrams from Terraform/CloudFormation

    5. Consistency & Standards

    Enforce organizational standards with linters, templates, and style guides. Tools like markdownlint can validate diagram syntax.

    6. Portability & Tool Independence

    Plain text files work anywhere—no special software needed. Render in VS Code, GitHub, GitLab, Notion, Confluence, or custom tools.

    7. Cost Savings

    Most DaC tools are free and open source (Mermaid, PlantUML, D2). No per-user licensing costs.

    8. Accessibility

    Text-based formats are screen-reader friendly and easier to search/index than images.

    ⚡ Real-World Impact: Teams using Diagram as Code report 70% faster diagram creation, 50% reduction in outdated docs, and near-zero licensing costs.

    When to Use Diagram as Code

    ✅ Perfect for:

    • Software architecture diagrams (C4 models, microservices maps)
    • Flowcharts and state machines
    • Sequence diagrams and API interactions
    • Database schemas (ERDs)
    • Infrastructure diagrams (networks, cloud resources)
    • Git workflows and branching strategies
    • Technical documentation and ADRs (Architecture Decision Records)

    ⚠ Less ideal for:

    • Pixel-perfect marketing materials or presentations
    • Highly custom/artistic designs requiring fine-grained control
    • Diagrams with dozens of interconnected nodes (layout can be tricky)

    🧜 Mermaid

    tool javascript github

    What is Mermaid?

    Mermaid is the most popular DaC tool with native support in GitHub, GitLab, Notion, Obsidian, VS Code, and Confluence. It's JavaScript-based and renders in browsers.

    Key Features

    • ✅ Native GitHub/GitLab support: Renders directly in markdown files
    • ✅ Wide diagram types: Flowcharts, sequence, class, Gantt, ER, Git graphs, state, pie, journey maps
    • ✅ Browser-based: No server-side rendering needed
    • ✅ Active development: Frequent updates and large community
    • ✅ Live editor: https://mermaid.live for instant previews

    Syntax Example

    sequenceDiagram
    participant User
    participant API
    participant Database
    
    User->>API: POST /login
    API->>Database: Query user
    Database-->>API: User data
    API-->>User: JWT token

    Live Rendered Example

    sequenceDiagram participant User participant API participant Database User->>API: POST /login API->>Database: Query user Database-->>API: User data API-->>User: JWT token

    Use Cases

    • Embedding diagrams in GitHub READMEs
    • Technical documentation in static site generators (Docusaurus, VuePress, MkDocs)
    • Architecture Decision Records (ADRs)
    • Sprint planning (Gantt charts)

    Pros & Cons

    Pros Cons
    ✅ Best GitHub/GitLab integration ❌ Limited layout customization
    ✅ Huge ecosystem and community ❌ Large diagrams can be slow
    ✅ No installation needed (browser-based) ❌ Syntax can be verbose for complex diagrams
    ✅ Multiple diagram types ❌ Styling options less flexible than PlantUML

    What is PlantUML?

    PlantUML is the most mature and feature-rich DaC tool. It's been around since 2009 and supports an incredible variety of diagram types with extensive customization.

    Key Features

    • ✅ Most diagram types: UML, C4, wireframes, mindmaps, timelines, JSON/YAML visualization
    • ✅ Highly customizable: Extensive styling, themes, and preprocessor macros
    • ✅ Java-based: Fast server-side rendering
    • ✅ Enterprise adoption: Used by Fortune 500 companies
    • ✅ Mature ecosystem: IntelliJ, VS Code, Confluence, Asciidoctor integrations

    Syntax Example

    @startuml
!include <C4/C4_Context>

Person(user, "Customer", "Uses the system")
System(app, "Mobile App", "Provides services")
System_Ext(payment, "Payment Gateway", "Processes payments")

Rel(user, app, "Uses")
Rel(app, payment, "Charges", "HTTPS")
@enduml

    • Comprehensive UML diagrams (class, component, deployment)

    ✅ Excellent C4 model support ❌ Steeper learning curve
    ✅ Powerful preprocessing (includes, macros) ❌ No native GitHub rendering
    ✅ Mature and stable ❌ Syntax can feel dated

    🏛 Structurizr

    What is Structurizr?

    Structurizr is the official tooling for C4 model diagrams, created by Simon Brown (C4 model creator). It provides both a DSL and programmatic APIs in Java, .NET, TypeScript, and more.

    Key Features

    • ✅ Official C4 tooling: Built specifically for C4 architecture models
    • ✅ Multiple interfaces: DSL, Java, .NET, TypeScript, Python APIs
    • ✅ Workspace model: Single model generates multiple views
    • ✅ ADR integration: Link Architecture Decision Records to diagrams
    • ✅ Cloud service: Hosted rendering and sharing at structurizr.com

    Syntax Example (DSL)

    workspace "E-commerce System" {
  model {
    user = person "Customer"
    system = softwareSystem "E-commerce Platform" {
      webapp = container "Web App" "React"
      api = container "API" "ASP.NET Core"
      database = container "Database" "PostgreSQL"
    }
    
    user -> webapp "Uses"
    webapp -> api "Calls" "HTTPS/JSON"
    api -> database "Reads/Writes"
  }
  
  views {
    systemContext system {
      include *
      autolayout lr
    }
    
    container system {
      include *
      autolayout lr
    }
  }
}

    Use Cases

    • C4 model architecture documentation
    • Enterprise architecture governance
    • System design documentation for large projects
    • Architecture reviews and audits

    Pros & Cons

    Pros Cons
    ✅ Best-in-class C4 support ❌ Focused only on architecture diagrams
    ✅ Model once, view many ways ❌ Cloud service has usage limits
    ✅ Programmatic API for code generation ❌ Steeper learning curve than Mermaid
    ✅ ADR integration ❌ Requires separate hosting/rendering

    🔷 Graphviz (DOT)

    tool classic graphs

    What is Graphviz?

    Graphviz is the oldest and most foundational graph visualization tool (since 1991). It uses the DOT language and is the rendering engine behind many other DaC tools.

    Key Features

    • ✅ Industry standard: Used by countless tools as a rendering backend
    • ✅ Powerful layouts: Hierarchical, circular, radial, force-directed
    • ✅ Language bindings: Python, Ruby, Java, JavaScript, Go, Rust
    • ✅ Extremely flexible: Fine-grained control over every aspect

    Syntax Example

    digraph Architecture {
  rankdir=LR;
  node [shape=box, style=filled];
  
  Frontend [fillcolor=lightblue];
  API [fillcolor=lightgreen];
  Database [fillcolor=lightyellow];
  Cache [fillcolor=orange];
  
  Frontend -> API [label="HTTP"];
  API -> Cache [label="Redis"];
  API -> Database [label="SQL"];
  Cache -> Database [label="miss"];
}

    Live Rendered Example

    Use Cases

    • Dependency graphs (package managers, build systems)
    • Call graphs and profiling visualizations
    • Data lineage and ETL pipelines
    • Academic papers and research diagrams

    Pros & Cons

    Pros Cons
    ✅ Extremely mature and stable ❌ Syntax can be verbose and cryptic
    ✅ Best layout algorithms ❌ Steep learning curve
    ✅ Wide language support ❌ Not designed for modern cloud/architecture diagrams
    ✅ Used by many other tools internally ❌ Dated visual styling

    Getting Started

brew install graphviz

    📐 C4 Model for Architecture

    framework architecture standard

    What is the C4 Model?

    The C4 Model is a framework for visualizing software architecture through four hierarchical diagram levels: Context, Container, Component, and Code.

    The Four Levels

    1️⃣ System Context

    • Highest level view
    • Shows system and users/external systems
    • Audience: Everyone (technical + non-technical)

    2️⃣ Container

    • Shows applications and data stores
    • Technology choices visible
    • Audience: Technical people inside/outside team

    3️⃣ Component

    • Breaks containers into components
    • Shows responsibilities
    • Audience: Software architects, developers

    4️⃣ Code

    • Class diagrams (optional)
    • Usually auto-generated from code
    • Audience: Developers

    Syntax Example

    package main

import (
    "github.com/blushft/go-diagrams/diagram"
    "github.com/blushft/go-diagrams/nodes/aws/compute"
    "github.com/blushft/go-diagrams/nodes/aws/database"
    "github.com/blushft/go-diagrams/nodes/aws/network"
)

func main() {
    d, _ := diagram.New(diagram.Filename("web-service"), 
                        diagram.Label("Web Service Architecture"),
                        diagram.Direction("LR"))

    dns := network.Route53("DNS")
    lb := network.Elb("Load Balancer")
    
    // Create cluster for web tier
    webCluster := diagram.NewGroup("Web Tier")
    web1 := compute.EC2("Web 1")
    web2 := compute.EC2("Web 2")
    web3 := compute.EC2("Web 3")
    webCluster.Add(web1, web2, web3)
    
    // Database tier
    dbCluster := diagram.NewGroup("Data Tier")
    primaryDB := database.RDS("Primary")
    replicaDB := database.RDS("Replica")
    dbCluster.Add(primaryDB, replicaDB)
    
    // Connect nodes
    d.Connect(dns, lb)
    d.Connect(lb, web1)
    d.Connect(lb, web2)
    d.Connect(lb, web3)
    d.Connect(web1, primaryDB)
    d.Connect(web2, primaryDB)
    d.Connect(web3, primaryDB)
    d.Connect(primaryDB, replicaDB).Label("Replication")
    
    d.Render()
}

    ✨ Best Practices

    practices guidelines standards

    General Principles

    1. Keep Diagrams Simple

    The Rule of Seven: Keep diagrams to ~7±2 elements. If you have more, break into multiple diagrams or use hierarchical views.

    • ✅ Good: One focused diagram per concern
    • ❌ Bad: Cramming 50 microservices into one diagram

    2. Store with Code

    Place diagram files in the same repo as code they document:

    my-app/
├── src/
├── docs/
│   ├── architecture/
│   │   ├── system-context.mmd
│   │   ├── container-diagram.mmd
│   │   └── deployment.d2
│   └── api/
│       └── sequence-login.mmd
└── README.md

    3. Update Diagrams with Code Changes

    Treat diagrams as code. When you update architecture, update diagrams in the same PR/commit.

    • Use PR templates with a "Documentation Updated" checkbox
    • Add diagram validation to CI (e.g., check syntax with mermaid-cli)

    4. Use Consistent Naming

    Adopt a naming convention for diagram files:

    # Good naming
system-context.c4.puml
auth-sequence.mmd
deployment-production.d2

# Bad naming
diagram1.mmd
untitled.puml
new-file-2.d2

    5. Add Metadata

    Include titles, dates, authors, and versions in diagrams:

    %%{init: {'theme':'base'}}%%
graph LR
    %% Title: E-commerce System Architecture
    %% Author: Architecture Team
    %% Last Updated: 2026-03-10
    %% Version: 2.0

    6. Use Color Sparingly

    Color should convey meaning, not just decoration:

    • 🟢 Green: Healthy/active systems
    • 🟡 Yellow: Staging/deprecated
    • 🔴 Red: Critical/external dependencies
    • ⚪ Gray: Inactive/planned

    7. Leverage Includes and Reuse

    For PlantUML, use includes to share common elements:

    @startuml
!include common-styles.iuml
!include aws-icons.iuml

' Your diagram here
@enduml

    8. Generate Diagrams in CI/CD

    Automate diagram rendering and publishing:

    # GitHub Actions example
name: Render Diagrams
on: [push]
jobs:
  render:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Render Mermaid
        uses: neenjaw/compile-mermaid-markdown-action@v1
      - name: Deploy to GitHub Pages
        uses: peaceiris/actions-gh-pages@v3

    9. Validate Syntax

    Add linting to catch errors early:

    # Validate Mermaid syntax
mmdc -i diagram.mmd --validate

# Validate PlantUML
plantuml -syntax diagram.puml

# Validate in CI
- run: find . -name "*.mmd" -exec mmdc -i {} --validate \;

    Add README files in diagram folders explaining what each diagram shows:

Audience: Stakeholders, new team members.

Audience: DevOps, SREs.

    ⚠ Common Pitfalls & Solutions

    troubleshooting mistakes gotchas

    Pitfall #1: Overly Complex Diagrams

    Problem: Trying to show everything in one diagram.

    Solution: Break into multiple views. Use the C4 model hierarchy (context → container → component → code).

    Pitfall #2: Inconsistent Tool Usage

    Problem: Different teams using different tools, making diagrams hard to maintain.

    Solution: Standardize on 1-2 tools organization-wide. Document in engineering guidelines.

    Pitfall #3: Forgetting to Update Diagrams

    Problem: Code evolves, diagrams don't.

    Solution:

    • Add "Update documentation" to Definition of Done
    • Include diagram files in PR templates
    • Use CI checks to validate diagram syntax
    • Make diagram updates part of code reviews

    Pitfall #4: No Naming Conventions

    Problem: Files named diagram1.mmd, untitled.puml, new.d2.

    Solution: Adopt a standard naming scheme:

    {system}-{type}-{environment}.{ext}

Examples:
auth-service-sequence-prod.mmd
payment-container-diagram.puml
infrastructure-deployment-aws.d2

    Pitfall #5: Ignoring Performance

    Problem: Large diagrams with 100+ nodes render slowly or not at all.

    Solution:

    • Break large diagrams into smaller, focused views
    • Use subgraphs/clusters to organize
    • Consider D2's TALA layout engine for large graphs
    • Pre-render diagrams to SVG/PNG for documentation sites

    Pitfall #6: Binary Diagram Formats in Git

    Problem: Storing rendered PNGs/SVGs in Git bloats repo size.

    Solution:

    • Store only source files (.mmd, .puml, .d2) in Git
    • Render diagrams in CI/CD pipelines
    • Use Git LFS if you must store rendered images

    Pitfall #7: No Diagram Ownership

    Problem: Nobody knows who to ask about outdated diagrams.

    Solution: Add CODEOWNERS for diagram folders:

    # CODEOWNERS
docs/architecture/ @architecture-team
docs/api/ @backend-team

    Pitfall #8: Hardcoding Secrets in Diagrams

    Problem: Accidentally including passwords, API keys in diagram labels.

    Solution:

    • Use placeholders: DB_PASSWORD instead of actual password
    • Add diagram files to secret scanning tools
    • Review diagrams in PRs for sensitive data

    Pitfall #9: Vendor Lock-In (Again)

    Problem: Using proprietary extensions or cloud-only features.

    Solution: Stick to open standards and self-hostable tools. Avoid features that only work on specific platforms.

    Pitfall #10: Not Leveraging Automation

    Problem: Manually updating dozens of diagrams.

    Solution:

    • Generate diagrams from code annotations
    • Use Structurizr/Terraform to create diagrams from architecture definitions
    • Automate screenshot generation for UI/flowcharts
