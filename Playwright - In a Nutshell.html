    📖 Introduction to Playwright

    overview introduction what-is

    Playwright is an open-source end-to-end testing framework for modern web applications, developed and maintained by Microsoft. It enables reliable, cross-browser automation with a single, unified API that works across Chromium, Firefox, and WebKit.

    What Makes Playwright Special

    FeatureDescription
    Cross-BrowserChromium (Chrome/Edge), Firefox, and WebKit (Safari) — all from one API
    Auto-WaitingAutomatically waits for elements to be actionable before interacting — eliminates flaky sleep() calls
    Network InterceptionIntercept, mock, and modify network requests and responses programmatically
    Multi-LanguageTypeScript, JavaScript, Python, .NET (C#), Java
    Parallel ExecutionRun tests in parallel across workers and browsers simultaneously with sharding
    Trace ViewerRich visual debugger with DOM snapshots, network logs, and action timeline
    CodegenRecord browser interactions and auto-generate test code instantly
    Mobile EmulationEmulate devices, geolocation, permissions, and viewport sizes

    Core Concepts

    ConceptDescription
    BrowserA browser instance (Chromium, Firefox, or WebKit)
    BrowserContextAn isolated browser session (like an incognito profile). Each test gets its own context
    PageA single browser tab or window within a context
    LocatorA lazy reference to an element — auto-retries on interaction
    ExpectAssertion library with built-in retry and web-first assertions
    FixtureReusable setup/teardown pieces injected into tests (page, context, browser)

    When to Use Playwright

    • ✅ End-to-end (E2E) tests simulating real user journeys
    • ✅ Cross-browser regression testing
    • ✅ Visual regression and screenshot comparison
    • ✅ API testing combined with UI workflows
    • ✅ Testing Single-Page Applications (React, Angular, Vue, Next.js)
    • ✅ Accessibility testing with ARIA-based locators
    Key Design Principle: Playwright's auto-wait mechanism eliminates the #1 cause of flaky tests — timing issues. Every action automatically waits for the element to be visible, enabled, stable, and not obscured before interacting.

    ✍️ Writing Tests

    basics first-test actions

    Anatomy of a Playwright Test

    import { test, expect } from '@playwright/test';

test('user can log in', async ({ page }) => {
  // 1. Navigate
  await page.goto('https://myapp.com/login');

  // 2. Interact
  await page.getByLabel('Email').fill('user@example.com');
  await page.getByLabel('Password').fill('secret');
  await page.getByRole('button', { name: 'Sign in' }).click();

  // 3. Assert
  await expect(page).toHaveURL('/dashboard');
  await expect(page.getByRole('heading')).toContainText('Welcome');
});

    Test Fixtures

    Playwright injects built-in fixtures into every test via destructuring:

    FixtureScopeDescription
    pageTestA fresh Page in an isolated BrowserContext
    contextTestThe BrowserContext for the current test
    browserWorkerA shared Browser instance (expensive to create)
    browserNameWorkerName of the current browser (e.g., 'chromium')
    requestTestAPI request context for making HTTP requests

    Grouping Tests with describe

    import { test, expect } from '@playwright/test';

test.describe('Shopping Cart', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/shop');
  });

  test('can add item to cart', async ({ page }) => {
    await page.getByText('Add to Cart').first().click();
    await expect(page.getByRole('status')).toContainText('1 item');
  });

  test('can remove item from cart', async ({ page }) => {
    await page.getByText('Add to Cart').first().click();
    await page.getByRole('button', { name: 'Remove' }).click();
    await expect(page.getByRole('status')).toContainText('0 items');
  });
});

    Test Hooks

    test.beforeAll(async ({ browser }) => {
  // Runs once before all tests in this file (worker scope)
});

test.afterAll(async () => {
  // Runs once after all tests in this file
});

test.beforeEach(async ({ page }) => {
  // Runs before each test — ideal for navigation/login
  await page.goto('/');
});

test.afterEach(async ({ page }, testInfo) => {
  // Runs after each test — ideal for cleanup
  if (testInfo.status !== testInfo.expectedStatus) {
    await page.screenshot({ path: `failure-${testInfo.title}.png` });
  }
});

    Custom Fixtures

    // fixtures.ts — extend base test with custom fixtures
import { test as base, expect } from '@playwright/test';

type MyFixtures = {
  loggedInPage: Page;
};

export const test = base.extend<MyFixtures>({
  loggedInPage: async ({ page }, use) => {
    await page.goto('/login');
    await page.getByLabel('Email').fill('admin@test.com');
    await page.getByLabel('Password').fill('password');
    await page.getByRole('button', { name: 'Login' }).click();
    await page.waitForURL('/dashboard');
    await use(page); // provide the fixture value to the test
    // teardown: nothing needed, context is isolated
  },
});

export { expect };

// my.spec.ts
import { test, expect } from './fixtures';

test('admin can view reports', async ({ loggedInPage }) => {
  await loggedInPage.getByRole('link', { name: 'Reports' }).click();
  await expect(loggedInPage).toHaveURL('/reports');
});
    Best Practice: Use test.beforeEach for lightweight setup like navigation. Use custom fixtures for heavier shared setup like authenticated sessions or database seeding — fixtures are automatically torn down and compose cleanly.

    🔍 Locators

    selectors finding-elements

    Locators are Playwright's primary mechanism to find and interact with elements. Unlike CSS/XPath selectors, locators auto-retry the query until the element becomes actionable — making tests resilient to timing issues.

    Recommended: User-Facing Locators

    Prefer locators that mirror how users perceive the UI — they're more resilient to code changes:

    LocatorExampleBest For
    getByRole()getByRole('button', { name: 'Submit' })Interactive elements — buttons, links, inputs, etc.
    getByLabel()getByLabel('Email address')Form fields associated with a label
    getByPlaceholder()getByPlaceholder('Search…')Inputs identified by placeholder text
    getByText()getByText('Welcome back!')Non-interactive text content
    getByAltText()getByAltText('Company logo')Images with alt attributes
    getByTitle()getByTitle('Close dialog')Elements with title attributes
    getByTestId()getByTestId('submit-btn')Elements with data-testid attribute

    CSS and XPath Locators

    // CSS selector
await page.locator('.nav-item.active').click();
await page.locator('input[type="email"]').fill('user@test.com');
await page.locator('#submit-button').click();

// XPath
await page.locator('xpath=//button[contains(text(),"Save")]').click();

// CSS :has() — find parent containing specific child
await page.locator('article:has(h2:text("Featured"))').click();

    Filtering Locators

    // Filter by text content
await page.getByRole('listitem').filter({ hasText: 'Product A' }).click();

// Filter by another locator
await page.getByRole('listitem')
  .filter({ has: page.getByRole('button', { name: 'Delete' }) })
  .first()
  .click();

// Combine filters (AND logic)
await page.getByRole('row')
  .filter({ hasText: 'Active' })
  .filter({ has: page.getByRole('checkbox', { checked: true }) })
  .count();

    Chaining and Scoping

    // Scope locator to a region
const sidebar = page.getByRole('navigation', { name: 'Sidebar' });
await sidebar.getByRole('link', { name: 'Dashboard' }).click();

// nth element (0-indexed)
await page.getByRole('listitem').nth(2).click();

// first() / last()
await page.getByRole('row').first().getByRole('button').click();

    Working with Multiple Elements

    // Count matching elements
const count = await page.getByRole('listitem').count();

// Get all text contents
const items = await page.getByRole('listitem').allTextContents();
// → ['Item 1', 'Item 2', 'Item 3']

// Loop over all matching elements
for (const row of await page.getByRole('row').all()) {
  const cells = await row.getByRole('cell').allTextContents();
  console.log(cells);
}

    Locator Priority Guide

    1. 🥇 getByRole() — mirrors ARIA; works with screen readers; most resilient
    2. 🥈 getByLabel() — clear semantic link to form fields
    3. 🥉 getByTestId() — stable if you own the code; add data-testid attributes
    4. ⚠️ getByText() — fine for static content; fragile if text changes frequently
    5. 🚫 CSS class selectors — avoid; class names change with refactors
    6. 🚫 XPath — verbose and brittle; last resort only

    🧪 Assertions

    expect verification checks

    Playwright's expect() provides web-first assertions that automatically retry until the condition is true (or the timeout expires). This eliminates the need for manual waits before assertions.

    Page Assertions

    import { expect } from '@playwright/test';

// URL assertions
await expect(page).toHaveURL('https://myapp.com/dashboard');
await expect(page).toHaveURL(/\/dashboard$/);

// Title assertions
await expect(page).toHaveTitle('My App - Dashboard');
await expect(page).toHaveTitle(/Dashboard/);

    Element Assertions (Most Common)

    AssertionDescription
    toBeVisible()Element is visible in the DOM
    toBeHidden()Element is not visible
    toBeEnabled()Form element is not disabled
    toBeDisabled()Form element is disabled
    toBeChecked()Checkbox/radio is checked
    toBeEmpty()Element or input has no content
    toHaveText()Element's text matches (supports regex)
    toContainText()Element's text contains the substring
    toHaveValue()Input/select has specific value
    toHaveAttribute()Element has attribute with value
    toHaveClass()Element has specific CSS class
    toHaveCount()Locator matches N elements
    toHaveScreenshot()Visual regression — pixel comparison
    toBeInViewport()Element is inside the visible viewport
    toBeAttached()Element is attached to DOM (may be hidden)

    Assertion Examples

    // Visibility
await expect(page.getByText('Success')).toBeVisible();
await expect(page.getByRole('dialog')).toBeHidden();

// Text content
await expect(page.getByRole('heading')).toHaveText('Dashboard');
await expect(page.getByRole('status')).toContainText('3 items');

// Input values
await expect(page.getByLabel('Email')).toHaveValue('user@example.com');

// Counts
await expect(page.getByRole('listitem')).toHaveCount(5);

// Attributes
await expect(page.getByRole('img')).toHaveAttribute('alt', 'Profile photo');

// State
await expect(page.getByRole('button', { name: 'Save' })).toBeEnabled();
await expect(page.getByRole('checkbox')).toBeChecked();

// Negative assertions
await expect(page.getByText('Error')).not.toBeVisible();

    Soft Assertions

    Soft assertions do not stop the test on failure — they collect all failures and report them at the end:

    test('full page audit', async ({ page }) => {
  await page.goto('/');

  // These won't stop the test on failure
  await expect.soft(page.getByText('Home')).toBeVisible();
  await expect.soft(page.getByRole('link', { name: 'About' })).toBeVisible();
  await expect.soft(page.getByRole('link', { name: 'Contact' })).toBeVisible();

  // Hard assertion — stops test if fails
  await expect(page).toHaveTitle(/My App/);
});

    API Response Assertions

    const response = await page.request.get('/api/users');
await expect(response).toBeOK();                    // status 200-299
expect(response.status()).toBe(200);
const body = await response.json();
expect(body.users).toHaveLength(10);
    Auto-Retry: Web-first assertions like toBeVisible() and toHaveText() automatically retry with a default 5-second timeout. This means you don't need to add manual waits before asserting on dynamic content — Playwright will poll until the condition is met or the timeout expires.

    ⚙️ Configuration

    config setup options

    playwright.config.ts — Full Example

    import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  // Test directory
  testDir: './tests',

  // Max time per test (ms)
  timeout: 30_000,

  // Fail the build on CI if you accidentally left test.only
  forbidOnly: !!process.env.CI,

  // Retry on CI
  retries: process.env.CI ? 2 : 0,

  // Number of parallel workers
  workers: process.env.CI ? 2 : undefined,

  // Global reporter
  reporter: [
    ['html'],
    ['github'],   // GitHub Actions annotations
  ],

  // Shared settings for all projects
  use: {
    baseURL: 'http://localhost:3000',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
    actionTimeout: 10_000,
    navigationTimeout: 30_000,
  },

  // Multi-browser projects
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit',   use: { ...devices['Desktop Safari'] } },
    { name: 'mobile-chrome', use: { ...devices['Pixel 5'] } },
    { name: 'mobile-safari', use: { ...devices['iPhone 13'] } },
  ],

  // Start dev server before tests
  webServer: {
    command: 'npm run start',
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
});

import { chromium } from '@playwright/test';

export default async function globalSetup() {
  const browser = await chromium.launch();
  const page = await browser.newPage();

}

  },

    📝 Trace Viewer

    debugging traces reports

    The Playwright Trace Viewer is an interactive GUI tool for investigating test failures. It records a complete trace of the test — every action, network request, DOM snapshot, and console log — so you can replay and inspect what happened step-by-step.

    Enabling Trace Recording

    // playwright.config.ts
export default defineConfig({
  use: {
    trace: 'on-first-retry',   // only record on first retry (recommended for CI)
    // trace: 'on',            // always record
    // trace: 'retain-on-failure', // keep only if test fails
    // trace: 'off',           // disable
  },
});

// Enable per-test
test('my test', async ({ page }) => {
  // traces can also be started/stopped manually
  await page.context().tracing.start({ screenshots: true, snapshots: true });
  await page.goto('/');
  // ... test actions
  await page.context().tracing.stop({ path: 'trace.zip' });
});

    Page Object Model (POM)

    Encapsulate page interactions in reusable classes to avoid duplication and improve maintainability:

    // pages/LoginPage.ts
import { Page, Locator } from '@playwright/test';

export class LoginPage {
  readonly page: Page;
  readonly emailInput: Locator;
  readonly passwordInput: Locator;
  readonly submitButton: Locator;
  readonly errorMessage: Locator;

  constructor(page: Page) {
    this.page = page;
    this.emailInput = page.getByLabel('Email');
    this.passwordInput = page.getByLabel('Password');
    this.submitButton = page.getByRole('button', { name: 'Sign in' });
    this.errorMessage = page.getByRole('alert');
  }

  async goto() {
    await this.page.goto('/login');
  }

  async login(email: string, password: string) {
    await this.emailInput.fill(email);
    await this.passwordInput.fill(password);
    await this.submitButton.click();
  }
}

// tests/login.spec.ts
import { test, expect } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

test('successful login', async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.goto();
  await loginPage.login('user@example.com', 'password');
  await expect(page).toHaveURL('/dashboard');
});

    Authentication Reuse (storageState)

    Avoid re-logging in before every test — save and reuse authentication state:

    // auth.setup.ts — run once, save auth state
import { test as setup } from '@playwright/test';

setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('user@test.com');
  await page.getByLabel('Password').fill('password');
  await page.getByRole('button', { name: 'Login' }).click();
  await page.waitForURL('/dashboard');
  await page.context().storageState({ path: '.auth/user.json' });
});

// playwright.config.ts — use saved state in all tests
projects: [
  { name: 'setup', testMatch: /auth\.setup\.ts/ },
  {
    name: 'authenticated',
    use: { storageState: '.auth/user.json' },
    dependencies: ['setup'],
  },
]

    The Dos and Don'ts

    ✅ Do❌ Don't
    Use getByRole(), getByLabel(), getByTestId()Use brittle CSS classes like .btn-primary-v2
    Use web-first assertions with auto-retryAdd await page.waitForTimeout(2000) before assertions
    Keep tests isolated — each test is independentShare state between tests in the same file
    Use storageState to reuse authenticationLog in via UI in every test's beforeEach
    Use mocks/intercepts for external APIsHit real external services in tests
    Clean up test data in afterEach or use isolated test accountsDepend on leftover data from previous tests
    Use test.describe to group related testsPut all tests in one giant spec file
    Use data-testid for elements with no semantic roleTarget inner implementation details like internal IDs
    Enable trace: 'on-first-retry' on CIDisable tracing and wonder why CI tests fail

  const email = `user-${Date.now()}@test.com`; // unique per run

    Handling Dynamic Content

    // ✅ Let Playwright auto-wait — just interact
await page.getByRole('button', { name: 'Load More' }).click();
await expect(page.getByRole('listitem')).toHaveCount(20);

// ✅ Wait for network idle after navigation

    Sharding Across Multiple Machines

    # Use matrix strategy to run shards in parallel
jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3, 4]   # 4 parallel machines

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test --shard=${{ matrix.shard }}/4

      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: blob-report-${{ matrix.shard }}
          path: blob-report/
          retention-days: 1

  merge-reports:
    needs: [test]
    runs-on: ubuntu-latest
    if: always()
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - uses: actions/download-artifact@v4
        with:
          path: all-blob-reports
          pattern: blob-report-*
          merge-multiple: true
      - run: npx playwright merge-reports --reporter html ./all-blob-reports
      - uses: actions/upload-artifact@v4
        with:
          name: html-report
          path: playwright-report/

    CI Best Practices

    • 🔁 Set retries: 2 on CI to handle transient infrastructure flakiness
    • 📸 Always upload playwright-report/ as a build artifact (even on failure)
    • 🔒 Use GitHub Secrets / Azure Key Vault for credentials; never hard-code them
    • ⚡ Use sharding to distribute large test suites across parallel machines
    • 🌐 Use webServer config to auto-start the app before tests run
    • 🔍 Use trace: 'on-first-retry' to capture traces for failing tests
    • 🏷️ Tag smoke tests with @smoke and run them on every PR; full suite on merge
    Tip: Use npx playwright test --reporter=github in GitHub Actions to get inline annotations on your pull request diff showing exactly which line of test code failed.

    IssueCauseSolution
    Element not found / timeoutElement not yet rendered or has wrong selectorUse Trace Viewer to inspect DOM; switch to getByRole()
    Flaky tests on CITiming / infrastructure varianceSet retries: 2; check for missing await; add waitForURL
    Tests pass locally, fail on CIDifferent screen resolution / fonts / env varsUse --headed locally to match CI; set explicit viewport; check env vars

    Browser binary not foundnpx playwright install not runRun npx playwright install --with-deps
    Auth state not persistingMissing storageState configUse page.context().storageState() + use.storageState in config
    Tests run slowlySequential execution / no parallelismSet fullyParallel: true; increase workers; use sharding on CI
